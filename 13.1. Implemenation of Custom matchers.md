# 📖 Custom Matcher Implementation in React Testing (Jest + Testing Library)

## **1. Introduction**

Custom matchers in Jest allow you to extend the `expect` API with your own domain-specific assertions.
In this example, we create a matcher called **`toContainRole`** to verify if a container element contains a certain number of elements having a specific [ARIA role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles).

---

## **2. Naming and Structure**

We define a **function** with the same name as the matcher:

```js
function toContainRole(container, role, quantity = 1) {
  // implementation
}
```

**Arguments:**

- **`container`** → The first argument to a matcher is always the value passed into `expect(...)`.
  In our case, this is an **HTML element** (like a `<form>` or `<div>`), which acts as the container in which we will search.
- **`role`** → The role we want to check for (`"button"`, `"link"`, `"textbox"`, etc.).
- **`quantity`** _(optional)_ → The expected count of elements with that role.
  Defaults to `1` for convenience (so users don’t always have to specify it).

**Why default to 1?**
It makes the matcher **less verbose** for common use cases.

---

## **3. Connecting the Matcher to Jest**

To register our matcher with Jest:

```js
expect.extend({
  toContainRole,
});
```

After this, you can use:

```js
expect(container).toContainRole('button', 2);
```

---

## **4. Matcher Return Format**

A custom matcher **must return** an object with:

- **`pass`** → `true` if the assertion passed, `false` otherwise.
- **`message`** → A function returning a string describing **why** it failed (only required if `pass: false`).

Example:

```js
return {
  pass: true,
  message: () => 'This is ignored when pass is true',
};
```

Or:

```js
return {
  pass: false,
  message: () => 'Expected container to contain 2 buttons, but found 0.',
};
```

---

## **5. Implementation**

### **Step-by-Step**

1. **Find all elements with the given role inside the container**
   We use `queryAllByRole` from Testing Library’s [within](https://testing-library.com/docs/dom-testing-library/api-within/) utility:

   ```js
   const elements = within(container).queryAllByRole(role);
   ```

2. **Compare the count to the expected quantity**

   ```js
   if (elements.length === quantity) {
     return { pass: true };
   }
   ```

3. **If mismatch, return failure with a descriptive message**

   ```js
   return {
     pass: false,
     message: () => `Expected to find ${quantity} ${role} element(s), but found ${elements.length}.`,
   };
   ```

---

## **6. Full Example Code**

```js
import { within } from '@testing-library/react';

function toContainRole(container, role, quantity = 1) {
  const elements = within(container).queryAllByRole(role);

  const pass = elements.length === quantity;

  if (pass) {
    return {
      pass: true,
      message: () => `Expected not to find ${quantity} ${role} element(s)`,
    };
  } else {
    return {
      pass: false,
      message: () => `Expected to find ${quantity} ${role} element(s), but found ${elements.length}.`,
    };
  }
}

expect.extend({ toContainRole });
```

---

## **7. Example Usage**

```js
// PASS case
expect(myFormElement).toContainRole('button', 2);

// FAIL case
expect(myFormElement).toContainRole('button', 1);
// Output: "Expected to find 1 button element(s), but found 2."
```

Test it with various scenarios:

  ```js

  ```

- ❌ **Wrong quantity**:



## **9. Benefits**

- **Domain-Specific Assertions** → Express test intent in natural language (`toContainRole` is self-explanatory).
- **Reusability** → No need to repeatedly write `queryAllByRole` + count checks in each test.
- **Better Failure Messages** → Automatically tells you the mismatch details.

---

## **10. Key Points to Remember**

- The **first argument** to a matcher is always whatever was passed to `expect(...)`.
- Default parameters make your matcher **easier to use**.
- Always provide **clear, descriptive failure messages**.
- Use Testing Library’s `within()` when searching inside a specific element.
- Extend Jest’s `expect` with `expect.extend({ ... })` before running tests.
- Matchers must return `{ pass, message }`.
- Use **template strings** for better message formatting.

---

## **11. Extra Tips**

- You can chain multiple queries if needed:

  ```js
  within(container)
    .getAllByRole('button')
    .filter((btn) => btn.disabled);
  ```

- If your matcher will be used often, put it in a **separate `matchers.js` file** and import it in your Jest setup file.
- For accessibility testing, use roles whenever possible instead of `className` or `id`.
