# **Absolute Last-Ditch `act` Solution in React Testing Library**

## **Context**

This note covers a **last-resort** method to fix `act` warnings in React tests using **`act()`** from React Testing Library.
This method **should almost never be used** — it's mainly educational for understanding how `act` works internally.

---

## **Key Points**

1. **Why Avoid This Solution**

   - This is **not a best practice**.
   - Only use if:

     - You have **urgent deadlines**.
     - You **cannot figure out** how to remove an `act` warning by other means.
     - Other preferred solutions (e.g., `findBy` queries, module mocks) are **not working**.

   - In professional projects, you should almost never encounter this case.

2. **Purpose of Demonstration**

   - To give insight into **how `act()` works** behind the scenes.
   - To help understand the timing window it creates for state updates in tests.

---

## **`act()` Background**

- **Origin**: Implemented by **`react-dom`**.
- **Role**:

  - Defines a "window" of time during which **state updates are expected**.
  - Ensures React flushes all effects and updates **before assertions run**.

- **In Testing Library**:

  - React Testing Library imports `act()` from `react-dom`.
  - Makes **small modifications**.
  - Re-exports it for use in tests.

---

## **Implementation Steps in the Transcript**

### **1. Prepare Test File**

- Remove `screen.debug()` calls (used earlier for debugging).
- Comment out **module mock** previously added (not using it for this demo).
- Import `act` from React Testing Library:

```js
import { act } from '@testing-library/react';
```

---

### **2. Create a Pause Utility**

- Shortened format for adding a small async delay.
- Purpose: simulate a small time window where updates can happen.
- Example:

```js
const pause = () => new Promise((resolve) => setTimeout(resolve, 100));
```

---

### **3. Wrap Updates in `act()`**

- Inside the test:

```js
await act(async () => {
  await pause();
});
```

**What happens here:**

- `act()` opens a window (100ms in this case).
- Any **state updates** during this window are considered **intentional and expected**.
- Prevents `act` warnings by signaling to React that updates are accounted for.

---

## **Behind the Scenes**

- Without `act()`, asynchronous state updates might **complete after** your test assertions.
- React warns because it assumes you are **asserting before updates are done**.
- `act()` explicitly tells React:

  > "I know an update will happen here — wait for it before continuing."

---

## **When to Use This**

✅ **Only when:**

- You’ve exhausted all other solutions (e.g., `findBy` instead of `getBy`, using async waits, proper mocks).
- You have a **critical need to run the test now**.
- It’s a **temporary fix** before refactoring to a proper solution.

❌ **Avoid if:**

- You can restructure your test to wait for elements with built-in async helpers.
- You can fix async state handling with better mocks or event triggers.

---

## **Why This Is a Bad Practice**

- **Hides real problems** in the test.
- Can **mask async timing issues**.
- Might make tests **pass incorrectly** (false positives).
- Reduces **test maintainability**.
- Not future-proof — changes in component timing could break it silently.

---

## **Preferred Solution**

- Use **`findBy` / `findAllBy` queries** from React Testing Library:

  ```js
  const element = await screen.findByText('Some text');
  ```

  - These automatically handle async waits.
  - Avoids the need for manual pauses or wrapping in `act()`.

- Use proper mocking for async functions (e.g., `fetch`, API calls).

## **Key Takeaways**

- **`act()`** is the low-level mechanism React uses to handle state updates during tests.
- React Testing Library's `findBy` queries already **handle `act` internally**.
- Manually using `act()` is a **last-resort emergency tool**, not a daily habit.
- Always aim to write **tests that don't need this hack**.
- Think of `act()` like a **fire extinguisher** — good to have, but if you need it every day, something is wrong.
