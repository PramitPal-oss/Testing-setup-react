# 📌 Custom Matchers in React Testing

## **Context**

- You already have a **working test** for your component.
- You make a **UI change** that unintentionally causes the test to fail.
- The test logic needs improvement for **better targeting** and **maintainability**.

---

## **The Change in Component**

1. Found the `<form>` in the component.
2. Wrapped the form with a `<div>`.
3. Added another **button** element _outside_ of the form:

   ```jsx
   <button>Go Back</button>
   ```

   - Represents a "leave the form" action.

---

## **Impact on the Test**

- Original test expected **2 buttons** in the component.
- Now there are **3 buttons**:

  - 2 inside the form (original)
  - 1 outside the form (new "Go Back" button)

- Test **fails** because it now counts all three.

---

## **Test Goal**

- Original goal: **Check only the form** and ensure it has exactly **2 buttons**.
- Options:

  1. **Change test goal** → Check for 3 buttons in the whole component.
  2. **Keep original goal** → Check _only_ inside the form for 2 buttons.

We stick to **Option 2** to match the original intent.

---

## **Solution: Using `within()`**

- `within()` is a helper from **React Testing Library** that allows **scoped queries** — i.e., finding elements _only inside_ a specific element.

**Example**:

```javascript
import { within } from '@testing-library/react';

// Find the form element
const form = screen.getByRole('form');

// Search for buttons only inside the form
const buttons = within(form).getAllByRole('button');

expect(buttons).toHaveLength(2);
```

✅ **Test passes** — now it ignores the extra button outside the form.

---

## **Automation Motivation**

- In large projects, you might write **similar tests repeatedly**.
- Constantly writing:

  ```javascript
  const form = screen.getByRole('form');
  const buttons = within(form).getAllByRole('button');
  expect(buttons).toHaveLength(2);
  ```

  becomes tedious.

- Solution: **Custom Matcher** → Makes the test **shorter** and **clearer**.

---

## **Goal for the Custom Matcher**

- Desired syntax:

  ```javascript
  expect(form).toContainRole('button', 2);
  ```

  Where:

  - `"button"` = role to search for.
  - `2` = expected number of elements with that role.

---

## **Why Custom Matchers?**

- **Jest** and **jest-dom** do not have a built-in matcher for:

  - Scoping search inside an element **and**
  - Checking role count in one call.

- Writing a custom matcher:

  - Reduces repetitive boilerplate.
  - Increases readability.
  - Makes intent **very explicit**.

---

## **Technical Plan**

1. **Name**: `toContainRole`
2. **Parameters**:

   - `roleName` → e.g., `"button"`, `"textbox"`, `"link"`.
   - `expectedCount` → integer.

3. **Implementation Flow**:

   - Use `within(element)` to scope the query.
   - Use `getAllByRole(roleName)` to find elements inside.
   - Compare length with `expectedCount`.
   - Return a clear **pass/fail message**.

---

## **Example Before Custom Matcher**

```javascript
const form = screen.getByRole('form');
const buttons = within(form).getAllByRole('button');
expect(buttons).toHaveLength(2);
```

---

## **Example After Custom Matcher**

```javascript
expect(screen.getByRole('form')).toContainRole('button', 2);
```

---

## **Advantages**

- **Less code** → single line instead of 3 lines.
- **Better readability** → test reads like plain English.
- **Scalability** → reusable across multiple tests.
- **Intent clarity** → easy for other developers to understand what is being tested.

---

## **Extra Notes**

- **`within()`** is essential when:

  - Multiple elements of the same role exist in the DOM.
  - You only care about a **subset** (inside a specific container).

- **Custom matchers** are registered via:

  ```javascript
  expect.extend({
    toContainRole(received, role, count) {
      // matcher logic
    },
  });
  ```

- **Good practice**:

  - Keep custom matchers in a separate `test-utils` or `jest.setup.js` file.
  - Add **clear error messages** in the matcher.
  - Use consistent naming patterns (`toHaveSomething`, `toContainSomething`).

---

## **Key Takeaways**

- When UI changes, tests can break for **unintended reasons** → scope queries properly.
- `within()` helps to **target queries** inside a specific element.
- If the same test pattern repeats often → create a **custom matcher**.
- Custom matchers improve **readability** and **reduce duplication**.
- Even if the code saving is small, **clarity and maintainability** in testing matter more.
