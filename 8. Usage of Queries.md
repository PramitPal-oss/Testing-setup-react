# 📒 Notes – When to Use `getBy`, `queryBy`, and `findBy` in Testing Library

## Overview

When writing tests with React Testing Library (or similar), **the choice of query function prefix** (`getBy`, `queryBy`, `findBy`) directly affects:

- The **behavior** when elements are present or absent.
- Whether the test **throws immediately** or **returns null**.
- How **assertions** should be structured.
- How to handle **synchronous vs. asynchronous** rendering (e.g., data fetching).

---

## 1️⃣ `getBy` and `getAllBy` – **Prove Element Exists**

**Use Case:**
When you want to confirm that an element **must** exist in the rendered output.

**Behavior:**

- Throws an **error immediately** if the element is **not found**.
- Will fail the test **before** assertions if the element is missing.

**Example:**

```js
const element = screen.getByRole('list');
expect(element).toBeInTheDocument();
```

**Key Insight:**

- If the element doesn’t exist, `getBy` throws → the test ends instantly.
- This means that the explicit assertion (`expect(...).toBeInTheDocument()`) is technically **redundant**, since the absence would already fail the test.

**Why Still Keep the Assertion?**

- **Maintain clarity**: The test reads as “find it, then assert it exists.”
- **Prevent silent failures**: If another engineer changes `getBy` to `queryBy`, the test would:

  - No longer throw on absence.
  - Pass incorrectly if the element is missing.

- The assertion acts as a **safety net**.

**Recommendation:**
✅ Always write the assertion, even if `getBy` already guarantees failure on absence.

---

## 2️⃣ `queryBy` and `queryAllBy` – **Prove Element Does NOT Exist**

**Use Case:**
When you want to confirm that an element is **absent**.

**Behavior:**

- Returns `null` if the element is not found (✅ no error thrown).
- Allows you to assert absence without breaking the test.

**Example:**

```js
const element = screen.queryByRole('textbox');
expect(element).not.toBeInTheDocument();
```

**Why Not Use `getBy` Here?**

- `getBy` throws when the element isn’t found → test fails **immediately**, even though absence is expected.
- `queryBy` is designed to handle the **“should not exist”** case without errors.

---

## 3️⃣ `findBy` and `findAllBy` – **Asynchronous / Data Fetching**

**Use Case:**
When the element will appear **after an async operation** (e.g., API call, delayed render).

**Behavior:**

- Returns a **Promise**.
- Waits for the element to appear **within a timeout**.
- Throws an error if not found after waiting.

**Example:**

```js
const element = await screen.findByRole('list');
expect(element).toBeInTheDocument();
```

**When to Use:**

- Testing **loading states** → element not present immediately.
- Testing UI after **data fetch** or **async rendering**.
- Avoid using `getBy` here — it will fail instantly before the element loads.

---

## ⚖️ Summary Table – Which Prefix to Use?

| Prefix       | When to Use                        | Throws if Missing?  | Async Support? |
| ------------ | ---------------------------------- | ------------------- | -------------- |
| `getBy`      | Prove **exists now**               | ✅ Yes              | ❌ No          |
| `getAllBy`   | Multiple elements exist now        | ✅ Yes              | ❌ No          |
| `queryBy`    | Prove **does not exist now**       | ❌ No               | ❌ No          |
| `queryAllBy` | Multiple elements should not exist | ❌ No               | ❌ No          |
| `findBy`     | Will appear **later** (async)      | ✅ Yes (after wait) | ✅ Yes         |
| `findAllBy`  | Multiple will appear later         | ✅ Yes (after wait) | ✅ Yes         |

---

## 📝 Best Practices

1. **Always keep assertions**, even when `getBy` guarantees an error.
2. Use `queryBy` for **absence checks** to avoid immediate failures.
3. Use `findBy` for **async elements** to handle fetch delays.
4. **Don’t mix** prefixes — keep tests explicit about intent.
5. **Document your reasoning** in tests to prevent accidental API changes.

---

## 🚨 Common Pitfalls & Gotchas

- **Accidental Passing Tests:**
  Switching from `getBy` to `queryBy` without updating assertions → missing elements may not cause test failure.

- **Async Without `findBy`:**
  Using `getBy` for async content causes **flaky tests** (fail before the element appears).

- **Redundant Assertions Debate:**
  Even if `getBy` throws on absence, keep the assertion to **future-proof** against code changes.

---

## 🧠 Mental Model

Think of them as:

- **`getBy`** → “I know you’re here — fail if not.”
- **`queryBy`** → “I’m just checking if you’re around — no panic if you’re not.”
- **`findBy`** → “I’ll wait until you show up.”
