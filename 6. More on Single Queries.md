# 📄 More on Single Queries – Detailed Notes

## 1️⃣ Recap – Understanding `getBy`, `queryBy`, `findBy`

- We have already seen **how these functions behave when finding zero elements**.
- Now:

  - We’ll **repeat the same process** for **finding exactly one element** and **finding more than one element**.
  - The flow will be quicker since the base concepts are already covered.

- **Reason for repetition** → These functions are **very common** in testing. You’ll need to understand them deeply to avoid confusion when reading documentation.

---

## 2️⃣ Finding **One** Element

We’re testing the behavior of **`getBy`**, **`queryBy`**, and **`findBy`** when exactly **one matching element** is found.

### Setup

- Example component: `ColorList` (contains **one `<ul>`** with role `"list"`, and inside it multiple `<li>` items).
- Test marked as `async` **right away** → because `findBy` is async.

```js
test('getBy, queryBy, findBy when finding ONE element', async () => {
  render(<ColorList />);

  // getByRole
  expect(screen.getByRole('list')).toBeInTheDocument();

  // queryByRole
  expect(screen.queryByRole('list')).toBeInTheDocument();

  // findByRole
  expect(await screen.findByRole('list')).toBeInTheDocument();
});
```

---

### Key Behaviors When **One Element** is Found:

| Method          | Behavior                                         | Return Type                   |
| --------------- | ------------------------------------------------ | ----------------------------- |
| **getByRole**   | Returns element immediately if found             | Element                       |
| **queryByRole** | Returns element immediately if found             | Element                       |
| **findByRole**  | Waits/retries until element appears (or timeout) | Promise → resolves to Element |

**Extra Notes**:

- **`findBy*`**:

  - Will keep **polling** for up to **1 second** until element appears.
  - Useful for **async rendering** scenarios (e.g., data from API).
  - Requires `await`.

- All three work **fine** when exactly one element matches.

## 3️⃣ Finding **More Than One** Element (when not intended)

We test what happens when **more than one element** matches the query.

### Setup:

- Still using `ColorList`.
- This time, target **`<li>`** elements (role `"listitem"`) → there are **three** in the component.

---

### Expected Behaviors:

| Method          | Behavior When **Multiple Matches**                          |
| --------------- | ----------------------------------------------------------- |
| **getByRole**   | ❌ Throws an error ("Found multiple elements with role...") |
| **queryByRole** | ❌ Throws an error (⚠️ same as getBy, NOT returning null)   |
| **findByRole**  | ❌ Throws an error after polling                            |

**Important**:

- The **only difference between `getBy*` and `queryBy*`** appears when **zero elements** are found:

  - `getBy*` → throws error
  - `queryBy*` → returns `null`

- But when **multiple elements** are found, **both throw errors**.

---

### Example Test:

```js
test('getBy, queryBy, findBy when finding MORE THAN ONE element', async () => {
  render(<ColorList />);

  // getByRole → throws
  expect(() => screen.getByRole('listitem')).toThrow();

  // queryByRole → throws (not null)
  expect(() => screen.queryByRole('listitem')).toThrow();

  // findByRole → throws (after async polling)
  await expect(screen.findByRole('listitem')).rejects.toThrow();
});
```

---

## 4️⃣ Why This Matters in Real Projects

- **Documentation confusion**:
  In the RTL docs, you often see:

  ```
  ByRole
  ByLabelText
  ByPlaceholderText
  ByText
  ```

  Without the `getBy`, `queryBy`, or `findBy` prefixes.

- This means **you must mentally combine**:

  - Query type (`getBy`, `queryBy`, `findBy`)
  - Search type (`Role`, `LabelText`, etc.)

**Example**:

- Docs show: `"ByLabelText"`.
- Available functions actually are:

  - `getByLabelText`
  - `queryByLabelText`
  - `findByLabelText`
  - and their plural forms (`getAllByLabelText`, etc.).

If you only see `"ByLabelText"` in the docs, it’s **not obvious** which variant to use unless you know the system.

## 5️⃣ Summary Table – Single Element Queries

| Variant    | Zero Matches         | One Match           | Multiple Matches | Async?        |
| ---------- | -------------------- | ------------------- | ---------------- | ------------- |
| `getBy*`   | ❌ Error             | ✅ Returns element  | ❌ Error         | No            |
| `queryBy*` | ✅ `null`            | ✅ Returns element  | ❌ Error         | No            |
| `findBy*`  | ❌ Rejects (timeout) | ✅ Resolves element | ❌ Rejects       | Yes (Promise) |

---

## 6️⃣ Key Takeaways

- Always choose the **right variant** based on:

  1. **Expected number of matches** (single vs multiple)
  2. **Timing** (synchronous vs asynchronous rendering)
  3. **Error handling needs**

- If you expect **multiple matches intentionally** → use the `getAllBy*`, `queryAllBy*`, `findAllBy*` variants (covered in next lesson).
- **Practical tip**: When debugging, try changing between `getBy`, `queryBy`, and `findBy` to understand **whether the problem is timing or absence of element**.
- **Doc navigation**: Remember that RTL docs often **omit** the prefix when listing query types.
