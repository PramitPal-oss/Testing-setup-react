# 📚 Notes: Using `act` (Hopefully Not!) with React Testing Library

## 1️⃣ **Context**

- This section addresses **item #4** in the overall learning sequence on `act` warnings.
- It’s considered **the most important point** regarding these warnings.
- Deals with how **React Testing Library (RTL)** and `act` function interplay in tests.

---

## 2️⃣ **What the Terminal Warning Says**

When you see an `act` warning in the terminal, it often looks like this:

```
Warning: An update to <ComponentName> inside a test was not wrapped in act(...).
```

It will then _suggest_ something like:

> If you want to update your state, you must do those events or initialize a state change inside of an `act` function.

**Key Point:**

- This is **extraordinarily misleading** for most RTL users.
- The official-looking terminal advice often tempts developers into calling `act` manually.
- Many blog posts and Stack Overflow answers **wrongly encourage** adding `act()` calls directly.

---

## 3️⃣ **Why You Should _Not_ Call `act` Manually (Most of the Time)**

- **With React Testing Library**, you almost _never_ need to call `act` yourself.
- RTL already wraps most interactions and rendering logic inside its own `act` calls.
- Manually adding `act` usually:

  - Adds unnecessary complexity.
  - Masks the real problem: **not waiting long enough for state changes.**

---

## 4️⃣ **When `act` Warnings Typically Occur**

- Most often seen when:

  - **Asynchronous operations** happen inside a `useEffect` (e.g., fetching data, timers, delayed state updates).
  - The test **checks for results too early** before the DOM is updated.

**Example Scenario:**

- A component fetches data in `useEffect`.
- Your test asserts on UI elements immediately after rendering.
- The component hasn’t finished updating → triggers an `act` warning.

---

## 5️⃣ **The Correct Way to Handle These Warnings**

Instead of calling `act` manually, **use RTL’s asynchronous utilities**:

- `findBy...`
  Waits for an element to appear, returns a Promise.
- `findAllBy...`
  Same as `findBy`, but for multiple matches.
- `waitFor`
  Waits for a condition to become true.
- **Avoid**:

  - `getBy...` and `getAllBy...` in async scenarios (synchronous lookups → cause premature checks).

---

## 6️⃣ **Why These Work**

- They inherently wrap their logic in `act`.
- They ensure the DOM has settled after state changes before continuing.
- They solve the root cause: **waiting for the UI to reflect async updates**.

---

## 7️⃣ **Rule of Thumb**

> **If you see an `act` warning in RTL tests, your fix is probably to _wait longer_ — not to call `act` manually.**

### ✅ DO:

- Use `findBy`, `findAllBy`, `waitFor`.
- Assert on the DOM **after** async UI changes are done.

### ❌ DON’T:

- Add `act()` around test code just because the terminal says so.
- Copy/paste Stack Overflow solutions that insert `act` everywhere.

---

## 8️⃣ **Mental Model**

- `act` is a low-level React testing API.
- RTL’s queries and helpers abstract away `act` usage.
- Warnings are usually a **signal of timing issues** in your test, not a missing API call.

---

## 9️⃣ **Summary Flow for Handling `act` Warnings**

1. **See warning** in terminal.
2. **Ignore the terminal’s advice** to manually call `act`.
3. Identify **what state update is pending** (often from async code in `useEffect`).
4. Use **RTL’s async query methods** to wait for the update.
5. Confirm the warning disappears.

---

## 🔍 Extra Insight

- React’s `act` ensures that **all effects, updates, and microtasks** are processed before assertions.
- RTL already integrates `act` for:

  - `render`
  - `fireEvent`
  - `userEvent`
  - Async queries

- Calling `act` manually can be useful **only** in rare, advanced cases (e.g., testing hooks directly without RTL helpers).

---

## 🧠 One-Year-From-Now Reminder

If you’ve forgotten all else:

> When testing with RTL, `act` warnings mean “wait for UI updates,” not “add `act()` yourself.”
> Reach for `findBy...` or `waitFor`, not `act()`.
