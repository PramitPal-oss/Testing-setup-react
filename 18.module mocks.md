````markdown
# Module Mocks in Jest — Detailed Notes

## **Purpose of This Technique**

The main goal here is to **avoid or remove a component from rendering** inside a test when:

- That component is causing `act(...)` warnings in React Testing Library (RTL).
- You don’t care about testing that problematic component for this test.
- Fixing the warning in the component itself is too complex or not possible in the current scope.

Instead of dealing with the actual implementation, **we replace the real component with a mock** that returns a placeholder.

---

## **Scenario in the Transcript**

- We are testing `RepositoriesListItem` component.
- This component **renders** another component called `FileIcon`.
- `FileIcon` is causing the `act(...)` warning in our tests.
- Our actual test’s goal **is NOT to test `FileIcon`**, but to test `RepositoriesListItem`.
- If we could **skip rendering `FileIcon`**, we would avoid the warning entirely.

---

## **The Jest `jest.mock()` Solution**

We use `jest.mock()` to **replace an imported module with a fake one**.

### **Syntax Recap**

```javascript
jest.mock(modulePath, factoryFunction);
```
````

- `modulePath`: The **relative path** to the file or module you want to mock.
- `factoryFunction`: A function returning the fake module contents.

---

## **Steps from the Transcript**

### **Step 1 — Identify the File to Mock**

We are inside:

```
repositories/RepositoriesListItem.test.js
```

The component we want to skip is:

```
repositories/tree/FileIcon.js
```

So the **relative path** from the test file to `FileIcon` is:

```javascript
'../tree/FileIcon';
```

---

### **Step 2 — Create the Jest Mock**

We define a mock at the **top of the test file**:

```javascript
jest.mock('../tree/FileIcon', () => {
  return () => 'FileIcon component';
});
```

**What’s happening here:**

1. `jest.mock('../tree/FileIcon', ...)`
   → Tells Jest: “Whenever someone imports `FileIcon`, don’t load the real one.”

2. `return () => 'FileIcon component';`
   → The mock will be **a function** (React functional component) returning a plain string instead of real JSX/HTML.

3. This means **in the DOM output**, instead of `<i>` tags or icons, we’ll just see the text:

   ```
   FileIcon component
   ```

---

### **Step 3 — How This Works in the Test**

- When `RepositoriesListItem` tries to import `FileIcon`, it now **receives the fake one**.
- The fake one renders instantly, no async behavior, no side effects → **no `act` warning**.
- The rest of the component (`RepositoriesListItem`) renders normally.

---

### **Step 4 — Verifying It Works**

1. Comment out your previous "findBy" / "findAllBy" workaround code that dealt with the act warning.
2. Run the tests.
3. The test should **pass** with **no act warning**.
4. Add:

   ```javascript
   screen.debug();
   ```

   to inspect the rendered output.

5. You will see:

   ```
   FileIcon component
   ```

   instead of the original HTML from the real `FileIcon` component.

---

## **Why This Works**

- **`act()` warnings** often happen when a component runs async state updates during rendering (e.g., fetching data, timers, animations).
- If you **skip rendering** the problematic component, those async updates **never occur**.
- Jest’s `mock()` replaces the import at the module resolution stage → the original file is never even loaded.

---

## **When to Use This Technique**

✅ **Good Use Cases:**

- You’re testing a parent component and don’t care about a child’s internal logic.
- The child component is tested separately in its own test file.
- The child component is causing complex side effects or async warnings.

❌ **Bad Use Cases:**

- The problematic component is the **main subject** of your test.
- You actually need to verify the child’s behavior in this test.

---

## **Extra Notes and Best Practices**

- **Mock Once or Globally:**
  If the same component causes trouble across multiple tests, you can:

  - Mock in each test file individually.
  - Or use a `__mocks__` folder for a global mock.

- **Static vs Dynamic Imports:**
  This only works if the problematic module is imported normally (`import FileIcon from ...`).
  If it’s dynamically loaded, mocking requires extra handling.

- **Restoring Mocks:**
  Use `jest.resetModules()` or `jest.restoreAllMocks()` between tests if needed.

- **Mocked Component Naming:**
  The returned string (`'FileIcon component'`) can be anything, but a clear placeholder helps debugging.

- **React Fragment Option:**
  Instead of a string, you can return minimal JSX:

  ```javascript
  () => <div data-testid='mock-file-icon' />;
  ```

## **Example in Context**

```javascript
// RepositoriesListItem.test.js

import { render, screen } from '@testing-library/react';
import RepositoriesListItem from './RepositoriesListItem';

// Mock FileIcon component to avoid act warnings
jest.mock('../tree/FileIcon', () => {
  return () => 'FileIcon component';
});

test('renders repository list item without act warning', () => {
  render(
    <RepositoriesListItem
      repository={
        {
          /* test repo data */
        }
      }
    />
  );

  screen.debug(); // Check output to see "FileIcon component"
});
```

---

## **Key Takeaways**

1. **`jest.mock()`** lets you completely bypass problematic components in your tests.
2. This is ideal when you don’t care about that component’s functionality in the current test.
3. Mocking helps eliminate unnecessary complexity and focus on the **unit under test**.
4. Be careful — if you mock something you actually need, your test becomes meaningless.
5. Always verify with `screen.debug()` to ensure the mock is active and behaving as expected.
