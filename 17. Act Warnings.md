# 📄 Solving the `act()` Warning in React Testing Library (RTL) – Detailed Notes

## 1. **Understanding the Problem**

- **What’s happening?**

  - You run tests in React Testing Library and see:

    ```
    Warning: An update to <SomeComponent> inside a test was not wrapped in act(...)
    ```

  - This occurs when **state updates** happen **after** the initial render but **outside** RTL’s awareness.

- **Root cause in this case:**

  - The warning mentions the `FileIcon` component.
  - That component:

    - Uses `useEffect` for **data fetching** (asynchronous).
    - Updates **state** after the promise resolves.

  - Classic cause of `act` warnings:

    > "useEffect → async code → setState after resolution"

---

## 2. **Best Practice Solution (Option #1 – Recommended)**

> **Always try this first. Other solutions are fallback options.**

### Goal

- **Detect when the component finishes data fetching**.
- Open an **`act` window** that covers the state update from that fetch.
- Use `findBy` or `findAllBy` query functions — these **wait for the element to appear**.

### Step-by-Step Process

#### Step 1 – Identify the Problematic Component

- Check the warning:

  - Example: `"An update to FileIcon component..."`.

- Locate it in the project:

  - Found in `repositoriesListItem`.
  - Passed a `name` prop with repository’s primary language.

- Open `FileIcon`:

  - Inside: `useEffect` + **Promise-based async code** + `setState` → ✅ warning source confirmed.

#### Step 2 – Compare Before and After States

- Temporarily:

  ```js
  await screen.debug(); // before
  await pause(100); // delay
  await screen.debug(); // after
  ```

- `pause` function:

  ```js
  const pause = () => new Promise((resolve) => setTimeout(resolve, 100));
  ```

- Observe output difference:

  - **Before:** `<div class="flex">...` → contains star icon SVG with `role="img"`.
  - **After:** new `<i>` element with:

    - `role="img"`
    - `aria-label="JavaScript"`

#### Step 3 – Detect the “After” State

- Use `findByRole` **with** a name filter:

  ```js
  await screen.findByRole('img', { name: /javascript/i });
  ```

  - `/javascript/i` is case-insensitive.

- Why add `name`?

  - Multiple `role="img"` exist (e.g., star SVG icon).
  - `findByRole('img')` alone finds the star SVG too early.
  - Name filter ensures we target the newly loaded icon.

---

## 3. **Why This Works**

- `findBy*` queries in RTL:

  - Return a **Promise** that resolves **when the element appears**.
  - Wrap in `act()` internally.
  - This means the state update **causing the element to appear** is properly “observed” by RTL → no warning.

---

## 4. **Key Observations / Patterns**

- You’ll likely face act warnings when:

  - `useEffect` + async work + `setState` after data fetch.

- If you control the component:

  - You already know what will appear when fetch finishes → write `findBy` queries directly.

- If you don’t control the component:

  - Use `screen.debug()` + delays to inspect before/after DOM.
  - Find a unique element/attribute to wait for.

---

## 5. **Fallback Methods (When `findBy` Is Hard)**

Sometimes:

- You can’t easily identify what DOM change occurs after data fetching.
- The async result may be deeply nested or indirect.

Other approaches:

- **Wait for absence** of loading state:

  ```js
  await waitForElementToBeRemoved(() => screen.getByText(/loading/i));
  ```

- **Wait for known side effects**:

  - Example: a class change or container height change.

- **Manual `act()`** (less clean, last resort):

  ```js
  await act(async () => {
    await pause(200);
  });
  ```

---

## 6. **Example – Obvious Case**

If you’re testing a component that fetches a list of users:

```js
const users = await screen.findAllByRole('listitem');
expect(users).toHaveLength(3);
```

- Here, `findAllByRole('listitem')` will wait until users are rendered.

---

## 7. **General Troubleshooting Workflow**

1. **Read the warning carefully** → find the component name.
2. **Locate that component** → look for `useEffect` + async + `setState`.
3. **Render test** with `screen.debug()` before & after small pause.
4. **Compare DOMs** to find a unique change.
5. Replace pause with `findBy`/`findAllBy` targeting that unique change.
6. **Rerun test** → warning should disappear.

---

## 8. **Extra Tips**

- **Don’t** blindly suppress act warnings — they point to **real timing issues**.
- **Use RegExp in queries** to make tests more resilient (case-insensitive matching).
- **Avoid fixed `setTimeout` delays in final tests** — they make tests slower and flaky.
- **Use ARIA roles/names** rather than classes or IDs if possible — tests will be more accessible and stable.

---

## 9. **Mental Model**

Think of `act()` as:

> “A container for all the UI updates my test code should wait for.”

When you use `findBy`, `waitFor`, `waitForElementToBeRemoved`, RTL **does `act()` for you** automatically.
When you don’t, and a state update happens later, RTL yells at you with an act warning.

---

### ✅ Final Takeaway

- **First choice:** `findBy` / `findAllBy` for a specific post-fetch element.
- **Fallbacks:** `waitForElementToBeRemoved`, `waitFor`, manual `act()` (only if necessary).
- Always identify **what changes in the DOM** after the async update — that’s your hook for the query.
