# Diving into Matchers in React Testing – Detailed Notes

## 1. Introduction

- This notebook is **faster** and more **interesting** compared to previous ones.
- Focus: **Matchers** in React Testing Library (RTL) and **custom matchers**.
- Matchers are functions **added to the end of an `expect` function** in tests.
- This lesson is not about going through _all_ matchers (since documentation already covers them well), but about **understanding them** and learning **how to create custom ones**.

---

## 2. What Are Matchers?

- **Definition:** Functions appended to `expect()` in testing, used to verify specific conditions.
- Example:

  ```js
  expect(element).toBeInTheDocument();
  ```

- **Matcher sources** in a Create React App (CRA) setup:

  - **Jest**: Provides general-purpose matchers.
  - **jest-dom**: Provides DOM-specific matchers for testing UI.

- **jest-dom matchers** are mostly for:

  - Checking DOM elements.
  - Ensuring visibility of elements.
  - Verifying presence in the DOM.

---

## 3. Common Example

- **`.toBeInTheDocument()`**
  Ensures a specific DOM element exists in the rendered output.

---

## 4. Why Not Learn All Matchers Now?

- **Reason:**

  - Documentation for Jest and jest-dom matchers is **clear** and **self-explanatory**.
  - The name of most matchers makes their function obvious.

- **Better Approach:**
  Learn **how to make your own matcher** for repetitive test patterns.

---

## 5. Why Create Custom Matchers?

- Reduces repetition when writing **similar tests**.
- Makes test code **more readable** and **maintainable**.
- Encapsulates logic into a reusable function.

## 7. Step-by-Step Example

### Step 1 – Imports

```js
import { screen, render, within } from '@testing-library/react';
```

- **`screen`**: Global test querying object.
- **`render`**: Renders React components into a virtual DOM for testing.
- **`within`**: Allows querying _within a specific element_ (important for nested queries).

---

### Step 2 – Component Creation

```jsx
function FormData() {
  return (
    <form aria-label='form'>
      <button>Save</button>
      <button>Cancel</button>
    </form>
  );
}
```

**Key points:**

- The `<form>` has `aria-label="form"`.

  - **Why?** Without an ARIA label, `getByRole('form')` won’t work.

- Two buttons: **Save** and **Cancel**.

---

### Step 3 – Rendering Component

```js
render(<FormData />);
```

- Ensures component renders in the test environment.

---

### Step 4 – Writing the Test

```js
test('the form displays two buttons', () => {
  render(<FormData />);

  const buttons = screen.getAllByRole('button');

  expect(buttons).toHaveLength(2);
});
```

**Explanation:**

- `getAllByRole('button')` finds all buttons.
- `toHaveLength(2)` ensures exactly 2 buttons are present.

---

## 8. Limitation Discovered

- At first, test **passes** without issue.
- But — if we make a **small change** to the component, the test might **break unexpectedly**.
- Example:

  - If another button is added outside the `<form>`, `getAllByRole` would count **all** buttons in the entire document, not just inside the form.

- This shows why **scoped queries** (e.g., with `within`) or **custom matchers** are important.

## 11. Extra Notes & Best Practices

- **`aria-label`**:

  - Crucial for accessibility **and** testing queries.
  - Makes components more usable for screen readers.

- **Avoid overly generic queries**:

  - `screen.getAllByRole('button')` checks entire DOM.
  - Instead, scope queries to a specific container:

    ```js
    const form = screen.getByRole('form');
    const buttons = within(form).getAllByRole('button');
    ```

- **When to write a custom matcher**:

  - If you repeat the same pattern in **3+ tests**.
  - If the test description matches a common assertion.
  - If you need to assert in **domain-specific** ways (e.g., “expect form to have exactly N buttons inside it”).
